# Lopmon v0.1 — Implementation Plan

Synthesized from clarifying answers + a 5-agent research workflow (web + discord.js docs).

## Locked decisions (from you)

| Question | Decision |
|---|---|
| Layout scope | **Skeleton only** — build `/create-role-signup`, `/mycolor` (renamed from `/role-color`), `/ping`. Mirror the layered layout. No redis, no calendar. |
| Color-role management | **Shared per-hex, reused + GC** — one role per distinct hex, shared by everyone who picks it; delete a color role when it has zero holders. |

## Feature designs

### `/create-role-signup @role "prompt"`  (staff-only)
- `default_member_permissions = ManageRoles` → only staff can post a panel; the button is for everyone.
- Posts a message with **one Button**, `customId = rolesignup:<roleId>`.
- A **single global `interactionCreate` router** toggles the role — **no collectors** (they die on restart). Stateless: the roleId rides in `customId`.
- `customId` is untrusted client input (≤100 chars). On every click re-validate: role still exists, not `@everyone`, not managed, and **below the bot's highest role**.
- Ephemeral confirm via `flags: MessageFlags.Ephemeral`.
- **Intents: `Guilds` only.** The invoking member (with roles) rides in the interaction payload — `GUILD_MEMBERS` is a privileged intent we do **not** need.

### `/mycolor <hex>`
- **hoist vs position — the spec conflated these.** Hoist only groups members in the sidebar; it does **not** set name color. Name color = the **highest-positioned _colored_ role**. So: `hoist:false`, win precedence by **position**.
- Canonicalize hex (`#`-strip, uppercase, expand 3→6 digit), validate `/^#?[0-9a-fA-F]{6}$/` with zod. Role name = `#RRGGBB`.
- **Shared roles, deduped by hex** (DB `color_role`). Reuse if the hex role exists, else create with the **new** `colors.primaryColor` API (`color`/`setColor` are deprecated) and `permissions: 0n`.
- **One color role per user** (DB `user_color`): remove the user's prior color role, add the new one.
- **GC** via DB refcount: after removing a user from the old role, if no `user_color` row still references it, delete the Discord role + its `color_role` row. Keeps total ≤ distinct colors in active use — well under the **250-role/guild cap** and clear of the role-create 24h lockout (>~250 creates/48h).
- Position the color band directly under the bot's role via one bulk `roles.setPositions()`.
- Needs **Manage Roles** + the bot's role dragged **above** the color band at setup (a bot can't move its own managed role or manage roles above itself).

## Open items (defaulted, revisit later)
- Arbitrary 16.7M hex allowed (not a curated palette); GC + 250-cap headroom handles sprawl.
- `/mycolor clear` supported to drop your color.
- Gradient/holographic (boosted-guild Enhanced Role Styles): **out of scope v0.1**, solid only.
- Commands **guild-scoped** (instant registration; single guild via `DISCORD_GUILD_ID`).
- `DISCORD_PUBLIC_KEY` is unused by a gateway bot (only for HTTP-interaction endpoints) — kept in env for parity.
