## WS1 — Security: signup panel privilege escalation (F1)

**File:** `src/discord/commands/create-role-signup.ts`

1. After the existing bot-side checks (line 41), add an invoker hierarchy gate mirroring Discord's native rule (strictly below your highest role; guild owner exempt; Administrator is NOT exempt — matches discord.js's own `GuildMember#manageable` logic):

```ts
const invoker = interaction.member
if (
  interaction.guild.ownerId !== invoker.id &&
  invoker.roles.highest.comparePositionTo(role) <= 0
) {
  throw new UserError('You can only create signups for roles below your own highest role.')
}
```

Verified: `interaction.member` is a full `GuildMember` after `inCachedGuild()` with a fresh roles snapshot from the interaction payload; `roles.highest` always exists (@everyone injected); position ties break by snowflake so `<= 0` only blocks the role itself. Enforcement is creation-time by design — the clicker is intentionally unprivileged. `setDefaultMemberPermissions(ManageRoles)` is only a default that server admins can override in Integrations settings, so this in-handler check is load-bearing.

2. Also reject **color roles** as signup targets: a signup button adds/removes roles with no `user_color` bookkeeping, so a panel for a color role lets clickers wear it invisibly to the GC refcount — GC would later delete the role off their backs. Add `ColorRepository.isColorRole(guildId, roleId): Promise<boolean>` (one indexed lookup) and throw a `UserError('That role is managed by /mycolor and cannot be used in a signup.')`.

3. Comment the residual: if an admin later drags the role above the creator's rank, existing panels still hand it out (same as every panel bot; admins can delete the message).

## WS2 — /mycolor state-integrity rework (F2–F6, F10, F11)

### 2a. Per-guild mutex serializing color mutations (F4, F5)

New `src/lib/keyedMutex.ts` — corrected implementation (the v1 sketch leaked unhandled rejections and had dead cleanup; both fixed):

```ts
/** Promise-chain mutex keyed by string. Do NOT nest withLock calls on the same key — deadlock. */
export function createKeyedMutex() {
  const tails = new Map<string, Promise<void>>()
  return function withLock<T>(key: string, fn: () => Promise<T>): Promise<T> {
    const prev = tails.get(key) ?? Promise.resolve()
    const run = prev.then(fn)
    const tail = run.then(
      () => undefined,
      () => undefined, // swallow here so the stored chain never rejects; callers still get `run`
    )
    tails.set(key, tail)
    void tail.then(() => {
      if (tails.get(key) === tail) tails.delete(key)
    })
    return run
  }
}
```

- Module-level instance in `mycolor.ts` (`const withGuildLock = createKeyedMutex()`) — NOT in `Deps` (single consumer; keeps deps.ts churn out of this workstream and matches WS3's module-level pattern).
- Wrap everything **after** `deferReply` (both the `clear` and set paths) in `withGuildLock(guild.id, async () => { ... })`. Deferring first is required: a queued lock wait must not eat the 3-second ack window. Errors thrown inside the lock propagate through the returned `run` promise to `interactionCreate`'s catch → `editReply` shows the `UserError` (traced).
- Why this closes both races: F4's find→create→insert and F5's count→delete sequences can no longer interleave with any other /mycolor mutation in the guild. Reentrancy audited: nothing inside the locked region dispatches another locked section.
- Rests on the single-process deployment (true for v0.1). Comment the multi-instance upgrade path: `pg_advisory_xact_lock(hashtext(guild_id))`. (A repo-level upsert-reconciliation was considered and cut: under the mutex it is permanently dead, untestable code, and multi-instance would need the advisory lock anyway because F5's race is not fixable by an insert conflict clause.)
- Keep `insertColorRole` as-is, with a comment that the mutex guarantees no conflict in-process.
- Add `logger.debug` on lock acquire/release for observability (also makes the manual concurrency smoke test interpretable).

### 2b. Stale-row cleanup must distinguish "role gone" from "fetch failed" (F4-adjacent, found in review)

`mycolor.ts:56` currently does `guild.roles.fetch(roleId).catch(() => null)`; a transient REST failure then triggers the stale-row branch (:58–62), deleting a **live** row and creating a duplicate role — the exact invariant violation WS2 exists to prevent, via the error path. Fix: only treat `DiscordAPIError` code 10011 (`RESTJSONErrorCodes.UnknownRole`) as role-gone; rethrow anything else (surfaces as the generic "try again" reply). Same discrimination 2c uses for delete.

### 2c. GC must not orphan roles (F2)

```ts
/** Elevated role + zero holders = the hex stays blocked until an admin demotes/deletes the
 *  role. Intentional: creating a second role for the hex would resurrect the duplicate-role
 *  bug the moment the old one is demoted. */
async function gcRoleIfUnused(deps: Deps, guild: Guild, roleId: string): Promise<void> {
  if ((await deps.colorRepo.countRoleHolders(guild.id, roleId)) > 0) return
  try {
    await guild.roles.delete(roleId, 'color role no longer used')
  } catch (error) {
    if (!(error instanceof DiscordAPIError && error.code === RESTJSONErrorCodes.UnknownRole)) {
      deps.logger.warn({ err: error, roleId }, 'gc: could not delete color role; keeping row')
      return // keep the row so dedup still tracks the live role
    }
    // 10011: role already gone — proceed to row cleanup
  }
  await deps.colorRepo.deleteColorRoleByRoleId(guild.id, roleId)
}
```

Verified: `roles.delete` on an already-deleted role yields 404/10011; `DiscordAPIError.code` carries the JSON error code.

/** Discord-side preconditions for the bot to assign/move/delete a role. */
export function botCanManageRole(me: GuildMember, role: Role): boolean {

    me.permissions.has(PermissionFlagsBits.ManageRoles) &&

## WS3 — Graceful shutdown (F7)

**Files:** `src/discord/events/interactionCreate.ts`, `src/index.ts`, `compose.yaml`.

1. In-flight tracking in `interactionCreate`: module-scoped `Set<Promise<void>>`. The wrapper promise must be created and added **synchronously at listener entry** (before any await — EventEmitter emits synchronously, so anything dispatched before the flag flips is guaranteed registered). The tracked promise wraps the **entire** dispatch including the catch/`handleError` path, so drain can't resolve while an error reply is still in flight.
2. `beginShutdown()` flips a module flag; while set, new interactions get an ephemeral "Restarting — try again in a moment." — this notice reply is itself gated on `isRepliable()`, wrapped in the tracked set, and `.catch(() => {})`-guarded (verified: `client.destroy()` nulls the REST token, so any untracked reply racing it becomes an unhandled rejection).
3. `drainInFlight(timeoutMs = 8_000): Promise<{ timedOut: boolean }>` — races `Promise.allSettled` of a **snapshot taken after the flag flips** against a timer (`unref()`d). It **resolves in both cases, never rejects**: a slow drain logs a warning and shutdown proceeds with exit 0 (abandoning writes at timeout is the SIGKILL alternative, not a failure — decided explicitly).
4. `index.ts`:

```ts
const shutdown = async (signal: string): Promise<void> => {
  if (shuttingDown) return
  shuttingDown = true
  logger.info({ signal }, 'shutting down')
  let code = 0
  try {
    beginShutdown()                              // stop dispatching new work
    const { timedOut } = await drainInFlight()   // let in-flight handlers finish their DB writes
    if (timedOut) logger.warn('drain timed out; proceeding')
    await client.destroy()                       // then drop gateway + REST
    await pool.end()                             // then close the pool nothing is using
  } catch (error) {
    logger.error({ err: error }, 'shutdown error')
    code = 1
  } finally {
    process.exit(code)
  }
}
```

Ordering is load-bearing: `client.destroy()` closes the gateway (code 1000) and nulls the REST token, so it must come **after** drain; `pool.end()` waits for checked-out clients, so it comes last.
5. `compose.yaml`: add `stop_grace_period: 30s` to the bot service — Docker's default 10s SIGKILLs a worst-case drain (8s) + destroy + pool.end, which would mask the exit code entirely.

## Known residuals (accepted, documented — not silently dropped)

1. A color role dragged above the bot with zero holders keeps its row and blocks that hex until an admin demotes/deletes it (intentional — the alternative resurrects duplicate roles).
2. A transiently-failed GC delete with zero holders leaves the Discord role until that hex is next adopted and cleared (no background reconcile sweep in v0.1).
3. If `roles.add` succeeds and `setUserRole` then throws, the role is orphaned on the member until the hex is re-adopted/cleared (pre-existing; sweep out of scope).
4. Signup panels created before WS1 for high roles keep working until deleted; admins moving roles above panel creators post-hoc is unpoliced (matches ecosystem norms).
5. `liftAsHighAsPossible` feeds computed positions into `setPositions` (raw-position PATCH) — coincide only in normalized guilds; degradation is logged (2g) but not fixed.
6. Multi-instance deployment requires replacing the in-process mutex with pg advisory locks (commented at the lock site).
